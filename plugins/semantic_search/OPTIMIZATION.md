# 语义搜索精度优化方案

现状：四张题材完全不同的图，搜「人像」，正确图 0.40、「原野」图 0.38。
Top-1 正确但区分度太小。本文按性价比排出优化阶梯，附具体改法。

## 一、先校准认知：0.2~0.4 是 CLIP 的正常区间

- CLIP 的图文余弦相似度**不是概率**，没有绝对含义。Chinese-CLIP ViT-B/16
  的典型分布：匹配对约 0.28~0.45，不匹配对也有 0.18~0.30。
- 所以「都是 0.2~0.4」本身不代表不准；要看的是**排序**和**间隔**。
- 本次测试 Top-1 是对的，说明链路正常；问题是间隔只有 0.02，
  换一批图或换个说法就可能翻车。下面的优化都围绕「拉开间隔」。

另一个要排查的点（已确认不成立）：曾怀疑「原野」图含人导致 0.38，
实际无人，因此 0.40 vs 0.38 是 ViT-B/16 单词查询的**真实弱区分度**，
更说明 L1/L3 必要。

## 二、万级规模下「阈值」怎么定（关键设计）

用户问得很到位：10k+ 张图、分数全挤在 0.2~0.4，凭什么划线说「算命中」？
结论先说：**绝大多数搜索场景根本不需要阈值；需要硬切分时也绝不手拍，
而是用评测集校准 + 查询相对归一化。**

### 2.1 搜索框 UX：只用 top-k 排序，不画硬线

人类探索式搜图（「找出沙滩照」）本质是**排名问题**：
返回 top-k（如 60 张）按相似度排好让用户滑着看即可，不需要
「是/否」二分类。此时阈值问题消失——你只要保证 Top-1/Top-10 召回率够高
（用 L4 评测集监控），展示层用 L2 的温度归一化给出「相对置信」辅助判断。

### 2.2 必须切分时（自动打标 / 过滤 / 批量操作）：两层手段

**A. 查询相对归一化（z-score）**——抗分布漂移。
同一次查询对 10k 张算出的余弦有均值 μ、标准差 σ；用
`z = (s - μ) / σ` 做相对判断：z > 2~3 才算「显著相似于背景」。
这样阈值对模型、画廊构成、查询长短都鲁棒，因为都以「本次查询的背景」
为参照，而不是一个写死的绝对数。

```python
sims = mat @ q            # (N,) 本次查询对全库余弦
mu, sd = sims.mean(), sims.std() + 1e-9
z = (sims - mu) / sd
keep = z > 2.5            # 仅保留显著相似者
```

**B. 评测集校准（L4 的延伸）**——决定那个 z 临界值到底取 2 还是 3、
或绝对分临界取多少。做法：
1. 建标注集（图→标签，查询→应命中标签），见 L4；
2. 对每类查询，量「真命中」与「背景」的得分分布，求 ROC/PR，
   取最大 F1 对应的分数或 z 值作为该校验点的阈值；
3. 把阈值存进插件 config（`min_confidence`），随模型/画廊变化重新拟合。

**一句话**：阈值不是「想」出来的，是**拿到标注集在模型上跑出来的**；
缺少这一步时，默认只用 top-k 展示、不做硬过滤。

### 2.3 性能：万级规模仍无需专用向量库

10k × 512 = 5MB 矩阵，一次 `mat @ q.T` 在 numpy 上是**个位数毫秒**；
10 万张约 ~100ms 仍可用。只有到百万级才需要 ANN（FAISS / sqlite-vec）。
所以「万级搜索」用现有暴力方案完全够，瓶颈是索引构建（见 API 文档阶段 1/2）
而非检索本身。

## 三、优化阶梯（按性价比排序）

### L1 查询模板扩展（零成本，建议必做）

单词抽象查询是区分度差的第一原因。CLIP 对自然短语远比对孤立名词敏感：
「人像」弱，「一张人像照片」「人物特写肖像照」强。

做法：文本侧一次编码多个模板，每张图取各模板得分的最大值
（best-match）或平均 softmax 概率：

```python
QUERY_TEMPLATES = [
    "{q}",              # 原样
    "一张{q}的照片",
    "{q}的照片",
    "这是{q}",          # 中文 CLIP 训练分布里的描述句式
]

def encode_query_multi(self, query: str) -> np.ndarray:
    texts = [t.format(q=query) for t in QUERY_TEMPLATES]
    return self.encode_texts(texts)   # (T, 512)，批量编码一次完成

# store.search 增加 multi_query 支持：mat @ Q.T -> (N, T)，按图取 max 再排序
```

改动点只在 encoder（加 encode_texts 批量文本编码）和 store.search
（接受 (T,512) 矩阵取列最大）。图片侧完全不动，索引不用重建。
预期效果：抽象词查询的间隔明显拉大，这是文献和实践中最稳定的免费提升。

### L2 用模型自带温度做归一化显示（配合 L1）

原始余弦不适合直接展示给用户。CLIP 训练时有可学习的 logit_scale
（Chinese-CLIP 约 exp(4.6)≈100），用它做 softmax 得到伪概率：

```python
scale = float(torch.exp(model.logit_scale.detach()).cpu())  # 读检查点真实值
probs = softmax(scores * scale)
```

效果：0.40 vs 0.38 的间隔在展示层变成约 7:1 的置信度比，
前端可以显示「87% 匹配」这类直观信息，也方便设阈值过滤低置信结果。
注意：只影响展示与阈值，不改变排序；不同检查点的 scale 要实测，
可在索引时把 scale 存进 meta 表。

### L3 升级 Chinese-CLIP ViT-L/14（一次性成本，效果最明显）

- 模型：`OFA-Sys/chinese-clip-vit-large-patch14`，768 维向量，
  权重约 1.3GB；RTX 5060 Laptop 推理毫无压力。
- 你的架构已为此做好准备：store 表有 dim 字段，search 时维度不符的
  旧向量自动跳过，换模型只需重建索引（`scan --rebuild`）。
- 向量体积依然忽略不计：3k × 768 × 4B ≈ 9MB。
- 预期：所有查询的区分度和召回都会上一档，尤其抽象词。
- download_model.py 把 MODEL_ID 和 CONFIG_FILES 抽成参数即可复用。

### L4 建立小评测集，停止凭感觉调参

凭四张图判断优化效果噪声太大。建一个固定评测集：

```
plugins/semantic_search/evalset/
    labels.json      # [{file, tags:["人像","室内","夜景"...]}, ...]
    queries.json     # [{"query":"人像", "expect_tags":["人像"]}, ...]
```

脚本计算 Recall@1 / Recall@5 / MRR，每次改动跑一遍对比。
20~50 张覆盖不同场景的图就够用，之后换模型、调模板都有数字依据。

### L5 混合检索（接入主程序后做）

语义通道与现有关键词 LIKE 搜索用 RRF（倒数排名融合）合并：
`score = Σ 1/(60 + rank_i)`。文件名/备注命中给确定性加权，
语义负责概念召回，互相补短。

### L6 低优先级

- 测试时增广（水平翻转再平均向量）：收益边际，索引时间翻倍，不建议先做。
- 编码源从原图换成缩略图缓存：不影响精度（CLIP 输入本来 ≤224px），
  只影响索引速度，属于接入阶段的性能项。

## 四、建议的实施顺序

1. L1 + L2 一起做（encoder/store/cli 小改，索引无需重建）
2. 用现有 test 文件夹人工复核，确认间隔改善
3. 做 L4 评测集，之后换 L3 大模型并量化对比
4. L5 留到正式接入阶段

## 五、一个诚实的预期管理

CLIP 类模型是「概念级粗检索」：沙滩/猫/日落/城市夜景这类查询效果好；
细粒度（同款包）、计数、文字内容、具体人物身份不行（后者需要你的人脸
mediapipe 管线配合）。优化只能拉开间隔、提高命中率，不能改变能力边界。
